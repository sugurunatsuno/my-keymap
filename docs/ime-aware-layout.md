# IME語尾拡張を前提とした配列最適化

記録日: 2026-11-18

## 採用する設計条件

- [U/E交換候補](../layouts/personal-colemak-derived-65-ue-swap-v2.json)を現在の評価基準にする。元配列は保持する。
- ユーザーはEffiveRoman式の「です」「ます」などの語尾拡張を実際に打ちやすいと感じている。打鍵感覚を設計上の重要な所感として残す。
- [35件の語尾拡張単語帳](../lexicons/effiveroman-suffixes.tsv)と[Google日本語入力用テーブル](../ime/google-japanese-input-effive-suffixes-35.txt)を評価に用いる。
- 小書きかなはL方式。通常ローマ字入力も残す。
- 中央寄りのキーの使いにくさと、キーの印字を見ながら入力する習慣を考慮する。

## 文字頻度ではなく実際に押すキーを数える

従来の単純な推定は `です -> desu`、`ます -> masu` を集計している。しかし拡張利用時の実際のキー列は `です -> ds`、`ます -> ms` となる。したがって、旧来のローマ字配列用ヒートマップだけで位置を最適化しない。

テキスト → 読み（かな）→ 使用する省略規則を適用した入力キー列 → 各キーの使用回数とキー間遷移 → 配列上の操作コスト、と順に評価する。

コーパスで省略を使用するか否かはユーザーの実際の入力率が未知なので、当初は以下を区別する:

- 省略なし: 通常ローマ字入力
- 試用8件: 対象語尾を入力するとき100%短縮を使うと仮定した理論上の比較
- 35件: 全拡張候補を使うと仮定した理論上の比較
- 将来、実測の使用率を得たら入力率を反映した評価も行う

複数の語尾が重なるときは打鍵数が最少となる分割を計算して重複計上を防ぐ。変換規則と実際のIME挙動の一致を後で確認する。

## 注目する組み合わせ

| 短縮 | かな | U/E交換候補上での初期着眼点 |
|---|---|---|
| `ds` | です | 左手内でのD→Sの移動、指の使い分け |
| `dn` | でした | 左手D→右手N |
| `ms` | ます | 中央寄りM→左手S |
| `mn` | ました | 右手M→Nの隣接入力 |
| `ht` | して | 下段H→左手T |
| `hs` | する | 下段H→左手S |
| `bs` | ません | 中央寄りB→左手S |

これらは位置関係の仮説にすぎない。実測されていない運指・速度改善を断定しない。特にMは中央寄りであるため、使用頻度と運動負担を分けて検証する。

## 最適化の順序

- IME拡張を適用する入力列生成器を追加する
- 元の配列とU/E交換候補で、通常入力と拡張入力の頻度差分ヒートマップを比較する
- 文字単体だけでなく、頻出キー遷移と手/指の移動負担を比較する
- ユーザーが打ちやすいと感じている短縮規則を維持することを優先し、改善の根拠が得られた場合だけD/M/N/Sなどの移動案を検証する
- 追加のFnレイヤースニペットはIME語尾拡張と重複しない候補を探す

まだ配列変更や解析コード変更は実装していない。
